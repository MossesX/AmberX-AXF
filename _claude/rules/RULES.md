# AmberX AXF rules

Project files (axhub-projects@1): `_claude/` ↔ `/projects/amberx-axf/_claude/` on the hub. Rules for every project
are in `_claude/shared/rules/`. Edit here, then `claude-sync sync`, then commit.

- **Pending builds:** check the pending list before any build (`node framework/cli/pending.mjs`, MCP `pending_list`, console → Pending builds). "Add to the pending build list" means park it.
- **Project manifests:** every project has `project.manifest.json` (project-manifest@1). This repo holds eleven: `amberx-axf` (root), `axf-demo`, `axf-console-web`, `axf-console-android`, `voice-vault`, `axhub-android`, `axhub-web`, `walkthrough-studio`, `amberx-droid`, `molly`, `expenses` (apps/). Only projects built with or for AmberX get a manifest; unrelated repos are never touched. **The build engine never loads or compiles a project without a validated manifest** (`requireProject` in `framework/cli/project.mjs`; app templates guard their dev/build too). Rules: `framework/schemas/project-rules.json`, managed in the Dev Console → **Standards**; locked rules can't be removed or loosened. Validators: `framework/core/project.ts` (reference), `framework/core/project-check.mjs`, Kotlin `ai.amberx.axf.kernel.project`; fixtures `framework/spec/fixtures/project-manifest.json`.
- **Shared data is on the hub:** the root manifest's `data.shared` (pending list, plan + media, build queue, catalog status, libraries index, project rules, tracker) is read and written in `/projects/amberx-axf/_data/<same path as in the repo>` where `/projects` is mounted (the Dev Console container), through `framework/cli/persist.mjs`. The repo copies are synced snapshots (`claude-sync sync`, then commit). On the VPS, change data through the CLI, console or MCP, not by editing repo files.
- **Everything visible is an asset** (`asset@1`). UI reads only engine-compiled tokens; never hardcode colours or sizes. Plugin and library UIs use theme tokens only (`framework/spec/THEMING.md`).
- **Plugins inherit the app's style (Oct 22 2026, Brett):** every plugin UI conforms to the style theme engine, so a plugin looks like the app it runs in: if the app changes its button style (button asset, style theme, spacing), every plugin's buttons change with it, and the same for every other control (sliders, switches, fields, containers, dialogs, menus, tabs). Plugins build controls only from the framework's components (`Button`, `Switch`, `TextField`, `SelectField`, `Container`, …) or its engine-styled classes (`fx-btn`, `fx-iconbtn`, …), never their own styled buttons or controls; a plugin's CSS may lay things out but never restyles a control. Same for libraries and every app on the framework.
- **Engine compatibility across ports is a hard constraint** (Android side paused, see "All Android work is on hold"): the Kotlin kernel and TS `framework/core` are the same design; change a reference engine, then regenerate `framework/spec/fixtures`.
- **Build options are `--switches`** from one registry (`framework/schemas/build-options.json`), each setting an asset token. Every future build defaults every option to off; existing files were set on. First option: `--wrap-groups`.
- **Every app gets a landing/loading screen and a settings interface by default.** Every app compiled by the build engine ships the settings interface and lib-settings.
- **Plugins:** each plugin gets a Plugin Manager entry (info, enable/disable, logs, settings). Plugins never ship their own settings screen, and never get a top-level settings tab: each plugin's settings are a **sub-tab of Settings → Plugins** (`SettingsTab.parent = 'plugins'`, enforced by the console for every plugin).
- **Every plugin can be removed completely (plugin-lifecycle@1, Oct 18 2026):** code only in its own folder, data only in its `lifecycle.dataDir`, doc lines outside it carry `<!-- axf-plugin:<folder> -->`, cross-plugin features only through capability services (`plugin_services`, e.g. `axf.llm@1`, `axf.agents@1`), never by folder name. Every plugin ships `install.mjs` + `uninstall.mjs` (and the shared Install & uninstall panel in its settings tab); `uninstall.mjs --all` must leave nothing behind and `node framework/cli/plugin-lifecycle.mjs check <folder> --after-uninstall` must pass. Guide: `apps/console-web/plugins/README.md` → Lifecycle.
- **UI-editing plugins: last save wins, fresh on focus (Oct 18 2026):** theme, style, layout, manager and builder plugins (`plugin.json` → `uiEditor`: theme/style/layout/manager/builder) may edit the same values. Saves are per key, and when two of them save the same key the **last save wins** (`SettingsRegistry.set` merges into what storage holds now, so a save never reverts other keys). Whenever one opens, loads or comes back into focus (window focus, tab visible, another tab saved), it **reloads current token values from settings** before showing them: `useEditorSync()` (`framework/react/editorSync.ts`) → `rt.refreshFromSaved()` (web) / `AxfRuntime.refreshFromSaved()` (Kotlin). Two enabled editors of one kind are shown as an info-level clash in the Plugin Manager, not an error.
- **Plugin Manager (Oct 18 2026; Fable rebuild Oct 20 2026):** the console's plugin manager is the `plugin-manager` plugin; its model is the cross-port `plugin-inventory@1` engine (`framework/core/engines/plugins.ts` = Kotlin `PluginInventoryEngine` = the plugin's `server/engine.py`, one fixture). It opens each plugin's UI and settings when they exist and lists dependencies in detail (what it needs and whether it's met, who provides it, who needs it, clashes). Every app's Settings → Plugins tab lists its libraries from the same engine; Android ships `PluginManagerModule` (axf-devtools). Links in menus are runtime contributions (`AxfWebLibrary.contextMenu`, `rt.addContextItems`), never edits to a context-menu asset.
- **No Fable rebuilds (Oct 27 2026, Brett; replaces "Opus now, Fable later"):** Claude decides when a step runs on Fable; Fable work is built on Fable, not on Opus with a parked Fable rebuild. Don't add Fable rebuild items to any list (shared rule "Claude decides when to use Fable").
- **Every rebuild ends with a differences report (Oct 20 2026):** after any rebuild (Fable rebuilds and every future one, any model), write `_claude/memory/docs/rebuilds/<pending-id>.md` comparing the new build with the version it replaced: what was removed, kept, changed and added; contract/API/asset/fixture changes; migrations and compatibility notes for apps already using it; tests before vs after; known gaps. Then show Brett the differences and improvements in chat (phone-readable summary, link to the report).
- **Rebuild log with screenshots (Oct 20 2026):** every rebuild also gets an entry in `_claude/memory/docs/rebuilds/LOG.md` (date, item, model, branch/commits, report link, screenshot folder, one-line summary). If any GUI is affected (web or Android), the report includes before/after screenshots in `_claude/memory/docs/rebuilds/<pending-id>/shots/{before,after}/` (phone and desktop) embedded in the report. Web: `node framework/cli/rebuild-shots.mjs --repo <checkout> --out <shots dir> --shots <shots.json> --label before|after` (before = the commit you started from). Android: **automatic** — push the rebuild branch (`fable/<id>`, `rebuild/<id>` or `harvest/<group>`) and `.github/workflows/rebuild-shots.yml` builds the affected apps at the base and the head, captures every nav screen on an emulator, and commits `<pending-id>/android.md` + `shots/android/{before,after}/<project>/` to that branch (`[skip ci]`); the report links `android.md`. Name rebuild branches that way and push them before merging.
- **Build orchestrator tracks every build (Oct 27 2026, Brett):** builds are broken into Fable / Opus steps in `_claude/builds/orchestrator.json` (orchestrator@1, see `_claude/builds/README.md`). Read it on load with THREADS.md, carry on from `orchestrator.mjs next`, tick steps with `act step`, and commit the tracker with the work. <!-- axf-plugin:build-orchestrator -->
- **Only the merge queue merges (Nov 4 2026, Brett; shared rule of the same name):** AmberX-AXF PRs land only through the push banner's merge queue (`apps/console-web/plugins/push-banner/land/merge-queue.mjs`, run by the `axf-auto-land` cron's `land.mjs run`); auto-land (`autoLand`, off by default since 0.7.1) and auto-merge stay off, no PR is updated from main outside the queue, and the console redeploys once per stack (`push-banner/queue-merging` holds the 5-minute updater). Report of the switch-over: `_claude/builds/reports/land-merge-queue-first.md`. <!-- axf-plugin:push-banner -->
- **Every step reaches main at once (Nov 3 2026, Brett: "every completed step, no matter how small, must reach the orchestrator and appear on main immediately"):** every builds store write (step ticked, status, note, branch, PR) is published to main straight away as a status-only commit by `framework/cli/builds-live.mjs` (store + journal + exports + one THREADS.md *Live build log* line, `[skip ci]`); this is the one exception to "every change through a PR", for status data only, never code. **No session trusts a branch's or main's export alone:** at start it runs `node framework/cli/builds-live.mjs sync` and `node framework/cli/builds-reconcile.mjs --apply` (the project SessionStart hook in `.claude/settings.json` does both; run them yourself where hooks don't run) and reads the store after. When a session pushes a branch or opens a PR for a build, it links it (`builds-live.mjs link <id> --branch <b> --pr <n>`; the reconciler also does it every 10 min). All steps done + PR open = `built` (awaiting merge); merged = `complete`. <!-- axf-plugin:build-orchestrator -->
- **Build profiles (Oct 27 2026, Brett):** the pending list, plan, build queue, tracking and orchestrator builds belong to the **active build profile** (since Nov 7 2026 just one: **All builds** (`all`, the base, active); Main framework, Current, Urgent, Angel, Big Dog, Breakroom and Refactor were merged into `all`, each build keeping `fromProfile`, and an old id anywhere resolves to `all`; the old profile folders are deleted and must not come back; `node framework/cli/profiles.mjs current`). Check which profile is in force before reading or adding work, add a build to the profile it belongs to (`AXF_BUILD_PROFILE=<id>` for one command), and never copy work between profiles unless Brett asks. Switching the saved profile is his call (console banner chip → Build profiles).
- **Small steps for big builds (Oct 21 2026):** every build (pending item, build-queue step, plan feature) estimated at more than 30 minutes is split into steps of 30 minutes or less, each with its own estimate, so it can be worked on little by little; builds of 30 minutes or less stay whole. This applies to existing items and to everything added later (adding a big item without steps is flagged; the console offers an AI draft of the steps when Claude is connected). Progress and time left show in the console's Build manager.
- **All Android work is on hold (Oct 21 2026, Brett):** no new Android code anywhere — no Kotlin/Compose features, kernel twins, Android modules or Android app changes (console app, AXHub included). **Exceptions: AmberX (`apps/amberx-droid`, its Capacitor shell; Brett, Oct 25 2026); Voice Vault (`apps/voicevault`) may be worked on again** (Brett, Oct 21 2026), Voice Vault's own app code only — framework Android code stays on hold. Builds are web/TS/Python only; a cross-port contract gets its Android twin recorded as a deferred gap in `framework/spec/PORTING.md` instead of written. Code already written and merged keeps compiling (CI still builds it, and a build break caused by a web change may be fixed). Brett finishes the Android side himself later.
- **Codebase changes log (Oct 21 2026, Brett):** every request to build, edit, remove or fix something gets an entry in the console's Codebase changes log (change-log@1, kept on axHub at `/projects/amberx-axf/_data/changes`). The Claude Code hook opens it and prints its id; without the hook, open one yourself: `node apps/console-web/plugins/codebase-changes/changes.mjs open "<title>" --kind build|edit|remove|fix`. Break the work into steps and record each as you go (`changes.mjs step <id|last> "<step>" --state running`, then `done`/`failed`/`skipped`), and record the result when you finish (`changes.mjs result <id|last> --state done|failed|partial|cancelled --summary "…" [--branch b] [--commit <sha>]… [--files N] [--test "name=before→after"]… [--link report=<path>]`). Closing an entry (taking it out of the banner) is Brett's call, not the session's. <!-- axf-plugin:codebase-changes -->
- **One banner on screen — embed@1 (Oct 21 2026, Brett):** an app shown inside another app's frame hides the chrome the host shows, its banner by default. Hosts mark what they embed (`EmbedEngine.userAgentSuffix` on a WebView's user agent, or `embedUrl` → `?axf-embed=<host>`); guests detect it (`rt.embedded`, automatic on the web) and apply the hide engine's forced layer, never touching the user's own saved choice. Settings grey the slot out ("Shown by <host>"). No app hosts others today (Patches, the first host, was retired Nov 3 2026). Engines on both ports, fixture `spec/fixtures/embed.json`.
- **One Banners settings (Oct 22 2026, Brett):** every banner plugin's settings are one interface (Settings → Plugins → Banners and the right-click Banner settings: a tab per banner with its look, behaviour and own settings). A new banner plugin declares `label`, `icon` and `settingsTab` on its banner so its settings join in.
- **Plugins a host makes unneeded aren't loaded (Oct 22 2026, Brett):** when an app runs inside a host (any app in a host's tab), plugins that would draw something the host already draws, or that the host makes unnecessary, aren't loaded on that page and are logged at launch. A plugin says when in its web library: `embed: { skipWhen: ['embedded' | 'take:<fn>' | 'hidden:<type>'] }` (`embedSkipReason` in `framework/core/engines/embed.ts`); `installLibraries` skips it, `rt.skippedLibraries` keeps why, the terminal gets one line each plus a summary, Settings → Plugins lists them. Page mode (an app's settings page in the host) never skips. Standalone everything loads. Every new plugin that only draws on chrome a host hides, or does a job a host takes, declares it.
- **Log every Claude change, with where it ran (Oct 23 2026, Brett):** every edit, create or remove Claude makes in the codebase, from any session, machine or environment (headless or not, VPS, cloud, claude.ai, console launches), is logged in the Codebase changes log with the machine, the session, the session type and full details (repo, branch, folder, what was asked). The hook opens an entry from prompt keywords and, since Oct 25 2026, on the first edit/create after any other prompt, with those details and the checkout's resume details (branch, commits, files) so another Claude account can carry on (`changes.mjs resume <id> --prompt`); a project-level hook so cloud and headless sessions log without a per-machine install is still a pending build (thread "Log every Claude code change", ~1.5 h, Opus recommended). Until it lands, open the entry yourself (`changes.mjs open`) and put the machine/session/surface in it. <!-- axf-plugin:codebase-changes -->
- **Build stats before you build (Oct 21 2026, Brett; shared rule "Report every build to axHub"):** before starting build work, record on that entry what it belongs to, the model and your estimates: `changes.mjs update <id> --ref pending:<id>|queue:<epic>|plan:<feature> --model <model> --estimate-min <minutes> [--estimate-cost <usd>] --areas "<folders you'll touch>" [--branch <b>]` (the cost defaults to minutes × the model's price heuristic in `framework/schemas/model-pricing.json`). Keep it live (steps as you go; the hooks send activity + a heartbeat) and finish with `result`; the Stop/SessionEnd hooks fill the actual tokens and cost from the session transcript. Sessions without a shell (claude.ai) write the same JSON through `axhub.memory_write` (`_claude/memory/docs/build-reporting.md`). Check the Build manager's **Live** list first: never start a build that is already running, and don't touch folders a running entry lists. <!-- axf-plugin:codebase-changes -->
- **One instance per plugin, model recorded (Oct 23 2026, Brett):** every plugin.json carries `builtWith: {model, builtAt}` (build-defaults@1 requires it) and shows a model badge wherever plugin info appears. Never install the same plugin twice, whatever model built it (same id, `builtWith.replaces`, folder stem or name = same plugin; `framework/cli/plugin-instances.mjs`): a rebuild by another model replaces the installed one in its folder through the confirmed swap (Plugin Update → Replace). Defaults like `opens: "main"` come from the build engine's registry `framework/schemas/build-defaults.json`, never from memory.
- **Extraordinary care for expansion:** placeholders everywhere, open registries, nothing in a build may constrain later scaling.
- AmberX-AXF is private. Don't create the separate console repo (`axf-console`, reserved in its manifest) until he says so.
- **The axHub badge is red unless settings come live from axHub (Oct 24 2026, Brett):** any axHub status badge or indicator starts **red** and turns **green** only while the app is reading its settings live from axHub right now (a fresh read of the hub's settings document succeeded, and a developer app's own hub source is ready). Repo copies, cached copies, local settings, a signed-out session or a read older than two check periods are red. Library: `framework/libs/hubstatus` (`hubLive` in `core.ts`).
- **Threads log in the repo (Oct 25 2026, Brett):** Claude builds everything in the repo, and `_claude/THREADS.md` is the threads and builds log every session reads on load and keeps current (thread, state, branch, PR, queued items). Update it and commit it with your work whenever a thread starts, changes state, opens or merges a PR, or queues an item, so any other session can pick the work up. **Widened Oct 26 2026 (Brett):** read it before doing anything, and update it whenever a thread is made, a session starts something, a build completes, tests start / pass / fail / stop part way, a push or pull is needed / completes / fails, a PR needs merging / is merged / the merge fails, a deploy is needed, anything fails, or the session runs out of credits or hits a usage limit (state `stopped`, with the step and how to resume). - **Attached things snap, never overlap (Oct 28 2026, Brett):** anything attached to a host (banner, toolbar, menubar; plugin badges, widgets, popups) never draws over or clips a neighbour. New hosts and new widget kinds follow the same rule (`framework/ui/axf.css`, banner section).
