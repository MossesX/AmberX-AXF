# AmberX AXF rules

Project files (axhub-projects@1): `_claude/` ↔ `/projects/amberx-axf/_claude/` on the hub. Rules for every project
are in `_claude/shared/rules/`. Edit here, then `claude-sync sync`, then commit.

- **Pending builds:** check the pending list before any build (`node framework/cli/pending.mjs`, MCP `pending_list`, console → Pending builds). "Add to the pending build list" means park it.
- **Project manifests:** every project has `project.manifest.json` (project-manifest@1). This repo holds four: `amberx-axf` (root), `axf-demo`, `axf-console-web`, `axf-console-android` (apps/). Only projects built with or for AmberX get a manifest; unrelated repos are never touched. **The build engine never loads or compiles a project without a validated manifest** (`requireProject` in `framework/cli/project.mjs`; app templates guard their dev/build too). Rules: `framework/schemas/project-rules.json`, managed in the Dev Console → **Standards**; locked rules can't be removed or loosened. Validators: `framework/core/project.ts` (reference), `framework/core/project-check.mjs`, Kotlin `ai.amberx.axf.kernel.project`; fixtures `framework/spec/fixtures/project-manifest.json`.
- **Shared data is on the hub:** the root manifest's `data.shared` (pending list, plan + media, build queue, catalog status, libraries index, project rules, tracker) is read and written in `/projects/amberx-axf/_data/<same path as in the repo>` where `/projects` is mounted (the Dev Console container), through `framework/cli/persist.mjs`. The repo copies are synced snapshots (`claude-sync sync`, then commit). On the VPS, change data through the CLI, console or MCP, not by editing repo files.
- **Everything visible is an asset** (`asset@1`). UI reads only engine-compiled tokens; never hardcode colours or sizes. Plugin and library UIs use theme tokens only (`framework/spec/THEMING.md`).
- **Engine compatibility across ports is a hard constraint** (Android side paused, see "All Android work is on hold"): the Kotlin kernel and TS `framework/core` are the same design; change a reference engine, then regenerate `framework/spec/fixtures`.
- **Build options are `--switches`** from one registry (`framework/schemas/build-options.json`), each setting an asset token. Every future build defaults every option to off; existing files were set on. First option: `--wrap-groups`.
- **Every app gets a landing/loading screen and a settings interface by default.** Every app compiled by the build engine ships the settings interface and lib-settings.
- **Plugins:** each plugin gets a Plugin Manager entry (info, enable/disable, logs, settings). Plugins never ship their own settings screen, and never get a top-level settings tab: each plugin's settings are a **sub-tab of Settings → Plugins** (`SettingsTab.parent = 'plugins'`, enforced by the console for every plugin).
- **Every plugin can be removed completely (plugin-lifecycle@1, Oct 18 2026):** code only in its own folder, data only in its `lifecycle.dataDir`, doc lines outside it carry `<!-- axf-plugin:<folder> -->`, cross-plugin features only through capability services (`plugin_services`, e.g. `axf.llm@1`, `axf.agents@1`), never by folder name. Every plugin ships `install.mjs` + `uninstall.mjs` (and the shared Install & uninstall panel in its settings tab); `uninstall.mjs --all` must leave nothing behind and `node framework/cli/plugin-lifecycle.mjs check <folder> --after-uninstall` must pass. Guide: `apps/console-web/plugins/README.md` → Lifecycle.
- **UI-editing plugins: last save wins, fresh on focus (Oct 18 2026):** theme, style, layout, manager and builder plugins (`plugin.json` → `uiEditor`: theme/style/layout/manager/builder) may edit the same values. Saves are per key, and when two of them save the same key the **last save wins** (`SettingsRegistry.set` merges into what storage holds now, so a save never reverts other keys). Whenever one opens, loads or comes back into focus (window focus, tab visible, another tab saved), it **reloads current token values from settings** before showing them: `useEditorSync()` (`framework/react/editorSync.ts`) → `rt.refreshFromSaved()` (web) / `AxfRuntime.refreshFromSaved()` (Kotlin). Two enabled editors of one kind are shown as an info-level clash in the Plugin Manager, not an error.
- **Plugin Manager (Oct 18 2026; Fable rebuild Oct 20 2026):** the console's plugin manager is the `plugin-manager` plugin; its model is the cross-port `plugin-inventory@1` engine (`framework/core/engines/plugins.ts` = Kotlin `PluginInventoryEngine` = the plugin's `server/engine.py`, one fixture). It opens each plugin's UI and settings when they exist and lists dependencies in detail (what it needs and whether it's met, who provides it, who needs it, clashes). Every app's Settings → Plugins tab lists its libraries from the same engine; Android ships `PluginManagerModule` (axf-devtools). Links in menus are runtime contributions (`AxfWebLibrary.contextMenu`, `rt.addContextItems`), never edits to a context-menu asset.
- **Opus now, Fable later:** when Brett asks to build something on Opus that is also parked for Fable, build it on Opus *and* add the Fable rebuild to the pending list; the Fable build starts by running the Opus version's uninstall script. **Only then** (Oct 19 2026): don't add a Fable rebuild to an Opus build out of habit. A rebuild is listed only when the item was parked for Fable first, Brett asks for one, or it's Fable work by the model rule (kernel internals, cross-port contracts, heavy refactors). Web-only console plugins and security work (Opus by the rule) get none.
- **Every rebuild ends with a differences report (Oct 20 2026):** after any rebuild (Fable rebuilds and every future one, any model), write `_claude/memory/docs/rebuilds/<pending-id>.md` comparing the new build with the version it replaced: what was removed, kept, changed and added; contract/API/asset/fixture changes; migrations and compatibility notes for apps already using it; tests before vs after; known gaps. Then show Brett the differences and improvements in chat (phone-readable summary, link to the report).
- **Rebuild log with screenshots (Oct 20 2026):** every rebuild also gets an entry in `_claude/memory/docs/rebuilds/LOG.md` (date, item, model, branch/commits, report link, screenshot folder, one-line summary). If any GUI is affected (web or Android), the report includes before/after screenshots in `_claude/memory/docs/rebuilds/<pending-id>/shots/{before,after}/` (phone and desktop) embedded in the report. Web: `node framework/cli/rebuild-shots.mjs --repo <checkout> --out <shots dir> --shots <shots.json> --label before|after` (before = the commit you started from). Android: **automatic** — push the rebuild branch (`fable/<id>`, `rebuild/<id>` or `harvest/<group>`) and `.github/workflows/rebuild-shots.yml` builds the affected apps at the base and the head, captures every nav screen on an emulator, and commits `<pending-id>/android.md` + `shots/android/{before,after}/<project>/` to that branch (`[skip ci]`); the report links `android.md`. Name rebuild branches that way and push them before merging.
- **Small steps for big builds (Oct 21 2026):** every build (pending item, build-queue step, plan feature) estimated at more than 30 minutes is split into steps of 30 minutes or less, each with its own estimate, so it can be worked on little by little; builds of 30 minutes or less stay whole. This applies to existing items and to everything added later (adding a big item without steps is flagged; the console offers an AI draft of the steps when Claude is connected). Progress and time left show in the console's Build manager.
- **All Android work is on hold (Oct 21 2026, Brett):** no new Android code anywhere — no Kotlin/Compose features, kernel twins, Android modules or Android app changes (console app, Build Pilot Android, AXHub, Voice Vault included). Builds are web/TS/Python only; a cross-port contract gets its Android twin recorded as a deferred gap in `framework/spec/PORTING.md` instead of written. Code already written and merged keeps compiling (CI still builds it, and a build break caused by a web change may be fixed). Brett finishes the Android side himself later.
- **Extraordinary care for expansion:** placeholders everywhere, open registries, nothing in a build may constrain later scaling.
- AmberX-AXF is private. Don't create the separate console repo (`axf-console`, reserved in its manifest) until he says so.
