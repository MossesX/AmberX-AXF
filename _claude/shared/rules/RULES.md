## Before building anything
- **Pick the model first.** Recommend Fable / Opus / Sonnet and say why, ask Brett to choose, and wait. Only the top three models. Fable for the strongest reasoning (kernel internals, cross-port contracts, heavy refactors). Opus for everything else, including anything security-adjacent (servers, shells, auth, deploy). Sonnet only when you're sure Opus isn't needed. You can't switch models yourself: if his pick differs, ask him to run `/model <name>`. **Ask every time (Oct 20 2026):** before each build, even small ones, recommend a model with one line of why and wait for his pick. **Fable where it makes a real difference (Oct 20 2026), including work that affects the GUI**: work that changes how GUIs work across apps (theme, layout, widget and banner engines, asset types, shared components, the React/Compose layers). Just making a GUI (a screen, banner, dialog or plugin UI built on the framework) is not a reason for Fable by itself: that's Opus.
- **Check the pending build list** before building. Builds parked until their model is available are listed in AmberX-AXF (`node framework/cli/pending.mjs`, MCP `pending_list`, console → Pending builds) and on the claude.ai Pending Builds page (https://claude.ai/artifact/HTwGSP7HcEt5yBd3MNz2Ye, db collection `builds`). "Add it to the pending list" means park it, don't build it.
- **Check the queue for clashes, and build related items together (Oct 21 2026, Brett):** whenever any session (any machine, any surface: VPS, cloud, headless, claude.ai, console launches) is asked to build anything or to put anything in the build queue, first go through everything still to build (pending list, build queue, plan; the console's Build manager shows them all) for items that touch the same files, features or contracts, or that would later conflict with, undo or redo what is being built. If any of them should be built at the same time, build them together in this build (tell Brett which ones and why before starting; when one of them is pinned to a different model, say so in the model pick), then take each one off the pending list / build queue (mark it complete with this build's branch/PR and tick its steps) so nothing is built twice. - **Fable suggested, Opus chosen = park a Fable rebuild (Oct 22 2026, Brett):** "Whenever Fable is suggested and Opus is chosen, add a rebuild in Fable." Whenever a model pick suggests Fable for a build (recommended, or offered as fitting the work) and Brett picks Opus, build it on Opus and add its Fable rebuild to the pending list (model Fable, split into steps of 30 min or less, a note naming the Opus build's branch/PR); the Fable build starts by removing or replacing the Opus version. Under a pass it still reads every rules file and `THREADS.md` from the repo first. No pass, no work, not even "just one quick change".
- **Every approval says what it's for (Oct 26 2026, Brett; axHub decision #99):** every axHub call that needs approval carries `reason: { title, description }` (title = what Brett is approving, one plain line; description = what it does and why). ## Projects
- **Every project has a manifest**, `project.manifest.json` (`project-manifest@1`, schema and rules in AmberX-AXF; rules are managed in the Dev Console → Standards). It names the project, its repo (even one that doesn't exist yet, for future naming) and its shared data. Its `name` is the project's folder on the hub, `/projects/<name>/`.
- **No project is loaded or compiled without a valid manifest.** The AXF build engine, the Dev Console and every template refuse to work on a project whose manifest fails validation.
- Every project has `_claude/` (memory/, instructions/, rules/, shared/) synced with `/projects/<name>/_claude/`, and its manifest's `data.shared` files synced with `/projects/<name>/_data/<same path>`.
