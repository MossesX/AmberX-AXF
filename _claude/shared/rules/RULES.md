These are shared files (axhub-projects@1). This folder syncs with `/projects/_shared/_claude/` on the hub and with
`_claude/shared/` in every project. Edit it in any project, then run `claude-sync sync`. Never store secrets.

## Code must conform to the asset system
- **Handwritten code conforms to the hot-swappable asset system (Oct 31 2026, Brett):** handwritten code is allowed, but only if it conforms to the hot-swappable asset system. Anything the build system makes through the console (templates, boilerplates, the plugin generator, Build Pilot, orchestrator and headless builds) is not handwritten by default: it is generated from framework controls and assets. Conforms means every visual value comes from hot-swappable assets and their tokens: the theme (colours and style, `--fx-*`), the scale (typography, density and sizing, compact by default and big enough to tap on a phone), layout, component styles, and the menu, toolbar and dialog assets. Use the framework's controls instead of raw ones (web: `Button`, `fx-btn`, `fx-chip`, `fx-seg__opt`…; Kotlin: `AxfButton`, `AxfTextField`…). No hardcoded px, rem or em sizes, spacing, fonts, radii, border widths or colours, and no `var()` fallbacks. Kotlin takes them from `Axf.colors`, `Axf.type`, `Axf.space` and `Axf.shapes`. Test: swapping any asset must restyle the code with no edits. CI enforces it on all web CSS/TSX and Kotlin UI, handwritten or generated (`node framework/cli/check-theme.mjs` and `check-controls.mjs` in AmberX-AXF name file:line and the token to use; `node framework/cli/scale-adopt.mjs <path>` moves most literals onto tokens). The build engine refuses to finish `axf init` on output that doesn't conform. Only the framework's own token and asset definition files are exempt. Code that is frozen (Android on hold, Patches paused) is held to a baseline that can only shrink (`framework/spec/conform-baseline.json`).
- **Every toolbar is a Toolbars plugin toolbar (Nov 3 2026, Brett: "it really works on a computer"):** every existing and future toolbar, in every app, gets per-toolbar settings and the Toolbar editor through its context menu, accepts dropped hooks, and uses **tap-to-confirm on touch only**: on a finger tap the first tap shows what the button does and arms it (lit, 3 s by default, configurable), a second tap on it within the window runs it, a tap on another button re-arms that one; mouse, trackpad, pen and keyboard stay a single click with the usual hover tooltip, decided per interaction (a touchscreen laptop: finger = double tap, mouse = single click). Destructive buttons keep their own confirm on top. Switching it off for a toolbar is a setting (Settings → Plugins → Toolbars, or that toolbar's own settings), never code. In AmberX-AXF the behaviour is the framework's (`framework/react/tapConfirm.ts` on `framework/core/engines/tapconfirm.ts`, installed by `<AxfProvider>` for every element with `role="toolbar"`), and `node framework/cli/check-toolbars.mjs` fails CI on a toolbar without `role="toolbar"` and a settings id, or one that turns the behaviour off in code without `data-axf-tap-confirm-reason`. Build `toolbar-tap-confirm` (Urgent).
- **Every tab group, toolbar, banner and navigation menu is an asset with an asset settings interface, reachable by right-click (Nov 4 2026, Brett: "all tab groups are supposed to be assets. With a settings interface, that's also an asset." + "navigation menus, toolbars, banners, are all asset types, and they all have a settings interface, which is an asset, and we can get to their settings by right-clicking all of them."; build `tab-group-assets`):** no hand-made tab rows anywhere (no `role="tablist"` / `fx-tabs` rows, no `<Segmented>` standing in for tabs): every row of tabs is the framework's `TabGroup` (`framework/react/components/TabGroup.tsx`, Kotlin twin deferred) drawn from the `tab-group` asset (tab-group@1: style incl. chips, position top / bottom / left / right, display icons + text / text / icons, overflow scroll / wrap / More menu / dropdown, size, sticky, collapsible, closable / reorderable where the host allows, count badges, remember last tab) with a stable settings id. Right-click / long-press on any tab group, toolbar, banner, navigation menu or menu bar opens the same block: **Settings…** (a dialog rendered through a `settings` asset = that kind's settings interface), **Change <kind>…** (asset picker) and **Move**. chrome-settings@1 (`framework/core/engines/chrome-settings-rules.mjs`): every chrome type with a settings interface (tab-group, toolbar, banner, nav-menu, app-menu, context-menu; an open list) ships **one shared default** `settings/chrome-<type>` in `framework/assets`, and **every app gets its own custom copy** `settings/chrome-<type>-<app>` made automatically (`axf init`; `node framework/cli/chrome-settings.mjs backfill` for existing apps) that `extends` the default until edited (inherit@1); **the shared default is selected by default** (Brett, addendum 3) and the picker always offers the default, the app's copy and *Reset custom to default*. Amber changes any of it by voice through the console actions `chrome.settings | chrome.pick | chrome.move | chrome.set | chrome.reset | chrome.swap | chrome.interface`. CI: `node framework/cli/check-chrome-assets.mjs` (hard-coded tab rows, navs without a settings id, banners outside the banner frame, toolbars without an id; ratchet `framework/spec/chrome-baseline.json`, counts only go down), `npx -y tsx framework/spec/check-tab-group.mts`, `check-chrome-settings.mts`, `node framework/cli/chrome-settings.mjs check`. <!-- axf-build:tab-group-assets -->

## Projects
- **Every project has a manifest**, `project.manifest.json` (`project-manifest@1`, schema and rules in AmberX-AXF; rules are managed in the Dev Console → Standards).
