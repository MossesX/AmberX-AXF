# Brett's rules (every project, every device)

These are shared files (axhub-projects@1). This folder syncs with `/projects/_shared/_claude/` on the hub and with
`_claude/shared/` in every project. Edit it in any project, then run `claude-sync sync`. Never store secrets.

## Before building anything
- **Models: the build orchestrator decides, per step (Oct 27 2026, Brett: "Forget previous model select rules"; replaces "Pick the model first" and "Ask every time").** Every build is broken into steps of 30 min or less in the Build orchestrator (`_claude/builds/orchestrator.json`, console → Builds → Build orchestrator, `apps/console-web/plugins/build-orchestrator/orchestrator.mjs`), each step pinned to **Fable** (cross-port contracts, kernel/engine internals, schema + migration design, heavy refactors, work that changes how GUIs work across apps) or **Opus** (everything else). Don't ask for a model per build. **Ask for approval (card) only at a model switch** between phases, then `orchestrator.mjs act approve <id> <phase>`. Save tokens: one session, no new session or sub-agent unless a step needs it, briefs carry only the current phase. You can't switch models yourself: at a switch, stop and give Brett the next phase's brief (`orchestrator.mjs brief <id>`) to run on that model. <!-- axf-plugin:build-orchestrator -->
- **Check the pending build list** before building. Builds parked until their model is available are listed in AmberX-AXF (`node framework/cli/pending.mjs`, MCP `pending_list`, console → Pending builds) and on the claude.ai Pending Builds page (https://claude.ai/artifact/HTwGSP7HcEt5yBd3MNz2Ye, db collection `builds`). "Add it to the pending list" means park it, don't build it.
- **Check the queue for clashes, and build related items together (Oct 21 2026, Brett):** whenever any session (any machine, any surface: VPS, cloud, headless, claude.ai, console launches) is asked to build anything or to put anything in the build queue, first go through everything still to build (pending list, build queue, plan; the console's Build manager shows them all) for items that touch the same files, features or contracts, or that would later conflict with, undo or redo what is being built. If any of them should be built at the same time, build them together in this build (tell Brett which ones and why before starting; when one of them is pinned to a different model, say so in the model pick), then take each one off the pending list / build queue (mark it complete with this build's branch/PR and tick its steps) so nothing is built twice. If an item would clash but shouldn't be built now, say so and add a note on that item. When adding to the queue, merge into an overlapping item instead of adding a duplicate.
- **Fable suggested, Opus chosen = park a Fable rebuild (Oct 22 2026, Brett):** "Whenever Fable is suggested and Opus is chosen, add a rebuild in Fable." Whenever a model pick suggests Fable for a build (recommended, or offered as fitting the work) and Brett picks Opus, build it on Opus and add its Fable rebuild to the pending list (model Fable, split into steps of 30 min or less, a note naming the Opus build's branch/PR); the Fable build starts by removing or replacing the Opus version. This holds even when he taps an "Opus only" option.
- **Load the rules and threads first, or stop (Oct 26 2026, Brett):** before doing anything else, every session loads the rules (`CLAUDE.md`, `_claude/shared/rules/RULES.md`, `_claude/rules/RULES.md`) and the threads log (`_claude/THREADS.md`) **from axHub** (`claude-sync`, or `axhub.memory_read` project `amberx-axf` / `axhub`, area `claude`). If it can't reach axHub, it does nothing except tell Brett and ask him for a go on axHub (AXHub web app → **Go pass**, https://axhub.amberxai.com/#/go-pass). Then it reads `GO-PASS.json` on the repo's `go-pass` branch (`git fetch origin go-pass` then `git show origin/go-pass:GO-PASS.json`, or GitHub) and works only while that pass says `"state": "go"` and its `expiresAt` is still ahead; it re-checks before each new step, and stops again when the pass ends or expires. Under a pass it still reads every rules file and `THREADS.md` from the repo first. No pass, no work, not even "just one quick change".
- **Every approval says what it's for (Oct 26 2026, Brett; axHub decision #99):** every axHub call that needs approval carries `reason: { title, description }` (title = what Brett is approving, one plain line; description = what it does and why). The approval page shows the title first, the description when expanded, and the exact code in its own collapsible section; a call without a reason is refused.
- Questions, explanations and quick lookups need no model pick.
- **One agent, no sub-agents (Oct 23 2026, Brett):** "Don't use sub-agents, just one agent. Don't spin it out and cost me all my tokens." Every session and thread does its work itself; never spawn sub-agents, parallel workers or deep-research fan-outs unless he asks for one by name. Tell every new thread this.

When he asks for something new mid-session, finish or park the current work, add a THREADS.md row for the new task, and give him a ready first message to start that thread; don't build it in the old session unless he says so.
- **Ask for a build profile, add it to the orchestrator first (Oct 27 2026, Brett; replaces the Oct 22 "goes on the Build manager list" rule):** "Anytime something is being built or edited or removed, anything that will change features and function, prompt for what build profile to send to orchestrator. - **Report every build to axHub before you start, and keep it live (Oct 21 2026, Brett):** any session anywhere (Claude Code on the VPS or any computer, headless runs, subagents, claude.ai chats, console launches) that is about to build, edit, remove or fix something first records it in the Build manager's log on axHub (`change-log@1`, `/projects/amberx-axf/_data/changes/<YYYY>/<MM>/<id>.json`, all projects): title, what it belongs to (`buildRef`), model, **time estimate (minutes) and cost estimate (USD)**, `status: running`, surface, host, branch and the folders it will touch (`areas`). Exact shape: `_claude/memory/docs/build-reporting.md` in AmberX-AXF. Don't start work the Build manager shows as running in another session, and don't touch the folders a running entry lists.  <!-- axf-plugin:codebase-changes -->

## Projects
- **Every project has a manifest**, `project.manifest.json` (`project-manifest@1`, schema and rules in AmberX-AXF; rules are managed in the Dev Console → Standards). It names the project, its repo (even one that doesn't exist yet, for future naming) and its shared data. Its `name` is the project's folder on the hub, `/projects/<name>/`.
- **No project is loaded or compiled without a valid manifest.** The AXF build engine, the Dev Console and every template refuse to work on a project whose manifest fails validation.
- Every project has `_claude/` (memory/, instructions/, rules/, shared/) synced with `/projects/<name>/_claude/`, and its manifest's `data.shared` files synced with `/projects/<name>/_data/<same path>`.

- **Send approvals once, never poll (Oct 28 2026, Brett; axHub decision #101; replaces the retry rule below once axHub PR #14 is deployed):** a call that needs approval is held by axHub (MCP `call` default `hold: true`): axHub keeps it and runs it itself when Brett taps Approve, or drops it on decline/expiry. Send it once with its `reason`, tell Brett what is waiting (one-tap approval link), then carry on with other work or end the turn. Until #101 is live, the old retry rule applies.
- **Veto calls are sent once and never polled (Brett, Oct 28 2026):** a veto call is held and run by the hub; read its result once at the end with get_job; never re-send. - **Approvals (Oct 20 2026):** whenever an axHub call needs his approval, open the approval screen for him (a browser tool when one reaches his device); otherwise give the direct one-tap link to that approval (`https://axhub.amberxai.com/auth/admin/approvals/<id>`) first, with the Coolify-terminal command as the fallback. **Don't wait for him to say "approved" (Oct 20 2026):** after giving the link, keep retrying the call with its confirmation id on your own until it runs or expires, then carry on. **Retry timing (Oct 21 2026):** the first 10 retries every 15 seconds, then every minute.
