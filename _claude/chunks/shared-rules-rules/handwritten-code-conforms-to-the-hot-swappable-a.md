## Code must conform to the asset system

- **Handwritten code conforms to the hot-swappable asset system (Oct 31 2026, Brett):** handwritten code is allowed, but only if it conforms to the hot-swappable asset system. Anything the build system makes through the console (templates, boilerplates, the plugin generator, Build Pilot, orchestrator and headless builds) is not handwritten by default: it is generated from framework controls and assets. Conforms means every visual value comes from hot-swappable assets and their tokens: the theme (colours and style, `--fx-*`), the scale (typography, density and sizing, compact by default and big enough to tap on a phone), layout, component styles, and the menu, toolbar and dialog assets. Use the framework's controls instead of raw ones (web: `Button`, `fx-btn`, `fx-chip`, `fx-seg__opt`…; Kotlin: `AxfButton`, `AxfTextField`…). No hardcoded px, rem or em sizes, spacing, fonts, radii, border widths or colours, and no `var()` fallbacks. Kotlin takes them from `Axf.colors`, `Axf.type`, `Axf.space` and `Axf.shapes`. Test: swapping any asset must restyle the code with no edits. CI enforces it on all web CSS/TSX and Kotlin UI, handwritten or generated (`node framework/cli/check-theme.mjs` and `check-controls.mjs` in AmberX-AXF name file:line and the token to use; `node framework/cli/scale-adopt.mjs <path>` moves most literals onto tokens). The build engine refuses to finish `axf init` on output that doesn't conform. Only the framework's own token and asset definition files are exempt. Code that is frozen (Android on hold, Patches paused) is held to a baseline that can only shrink (`framework/spec/conform-baseline.json`).
