# One true source: get the redundant settings out — Nov 21 2026

Build `one-true-source-get-redundant-settings`, branch `claude/one-true-source-get-redundant-settings`, Fable, one session.

## 1. Audit (step s1)

How it was made: `node framework/cli/settings-audit.mjs` (new) walks the console plugins, the console server and
shell, `deploy/`, `framework/cli`, `framework/core`, `framework/libs` and `framework/react` and lists

- the Claude settings registry (`apps/console-web/plugins/claude-settings/registry.json`, stored in the hub document
  `/projects/_shared/_data/claude/settings.json`, edited in Settings → Claude);
- framework settings (`{ key, label, kind }` declared for the settings registry, stored per user / device);
- module stores: every `DEFAULTS` / `SETTING_KEYS` literal of a plugin, CLI, deploy or core module (each is one JSON
  file in the shared store or the plugin's data folder);

and flags a key name that sits in more than one store and labels that say the same thing under different keys. The
full generated inventory is section 5. The live values quoted below were read on the VPS on Nov 21.

### Duplicate groups found

**(a) = one setting stored in more than one place · (b) = different keys that mean the same thing**

| # | What it is | Where it was stored | Screens / surfaces that edit it | Live values | Kind |
|---|---|---|---|---|---|
| 1 | How many builds run at once on the VPS | `agent-slots/build-limit.json` `maxBuilds` ("Hard limit: builds at once") · `agent-slots/settings.json` `maxAgents` ("Max running agents") | Settings → Plugins → Agent cap (two panels), Breakroom settings → Desks, `PUT agent-slots/hard-limit`, `PUT agent-slots/settings`, `build-limit.mjs set` | 6 · 6 | (b) |

What was actually wrong in each:

1. Two numbers for one job. The effective cap was always the smaller one, the two panels sat on the same screen under
   different wording, and the Builds page showed both ("Agent slots 5/6 · VPS limit 5/6").
2. Three numbers for one job, in three screens. The dispatcher used the pipeline's number and the worker launcher the
   Job routing one, so the smaller won without either screen saying so: Job routing shows hulu0241 and mossesx-max- at
   8, the dispatcher held both at 5. `builds.maxParallel` (1, set Nov 6) has been ignored since the pipeline file first
   carried a value; its label ("Max parallel builds") also described group 1, not what it fed.
3. The pipeline file's copy won over the Claude setting as soon as the file was saved once (every save writes every
   key), so the switch in Settings → Claude did nothing.
4. Same as 3: the file's copy shadowed the Claude setting.

### Looked at and not duplicates (kept apart on purpose)

| Keys | Why they stay separate |
|---|---|
| `pipeline stepsInParallel` (6) | Steps of one build at once: a per-build cap under group 1. Nothing else does this job. |
| `pipeline maxRuns` (5) · recovery watchdog `maxRetries` (3) · watchdog 2 `maxAttempts` · lander `maxAttempts` / `maxFixes` · auto-lander policy `maxAttempts` · retry ladder `maxAttempts` | Each counts something else (sessions per build in total; crashes since the last ticked step; attempts per Pipeline 2.0 step; landing attempts per PR). They are one family and their wording was close ("Max runs", "Max retries"); the wording is made distinct in s3, the counters are not merged because the contracts (build-watchdog@1, pipeline-2@1, lander) define them separately. |
| `agent-slots maxHeavy` (2) | Heavy steps (vite, docker tests, Playwright) at once: a different resource. |
| `build-limit emergencySlots` (2) | A second, separately counted pool. |
| Same key names in two files of one plugin (`agent-slots` server allow-list + engine defaults; `plugin-manager/server/lazy.py` + `src/lazyEngine.ts`; `skin-gallery.mjs` + `web/settings.ts`; `recovery-watchdog.mjs` on `build-watchdog.mjs`; `headless-context.mjs` defaults for the Claude `headless.*` keys) | One stored value each; the second file is the allow-list or the default table of the same store in another language. Not a second copy of the value. |
| `enabled`, `on`, `sound`, `tools`, `project`, `intervalMin`, `graceMin` in unrelated plugins | Common names in separate features (each store is its own file). |
| `noWait.night*` and `notify.quiet*` | Two different windows (approvals without waiting vs. phone pushes). |
| Console control's "Lander: …" / "Watchdog: …" / "Gate: …" labels (`gate/web/settingsStore.ts`, `build-orchestrator/web/watchdog.tsx`) | The same stored keys as the settings panels, registered for the console-wide command list where a bare "First wait" would be ambiguous. One store, a qualified label. |

Also found while auditing (fixed in s3): the console container has `ps`, so `build-limit.mjs` took the container's own
process list for the host's and reported **0 builds running** ("VPS limit 0 of 6") while five were building, and wrote
that zero over the host's snapshot until the enforcer's next pass.
