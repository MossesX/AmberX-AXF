## 2. Merged: one stored key each (step s2)

| Setting (the one wording) | The one stored key | Old keys, now read aliases | Migration |
|---|---|---|---|
| **Builds at once** | `<agent-slots dir>/build-limit.json` `maxBuilds` (Brett only) | agent-slots `settings.json` `maxAgents` | `migrateBuildsAtOnce()` in `framework/cli/agent-slots.mjs`, on the first read that finds both |
| **Sessions per account** | claude-workers `workers.json` `limits.building`; an account's own number `perAccount.<name>.building` | pipeline `settings.json` `parallelPerAccount` · pipeline `accounts.json` `<name>.parallel` · Claude setting `builds.maxParallel` (no longer registered) | `migrateSettings()` in the orchestrator's `pipeline.mjs`, on the host's dispatcher tick |
| **Launch builds without asking** | Claude setting `builds.launchWithoutAsking` | pipeline `settings.json` `autoQueue` | `migrateSettings()` |
| **Max launch brief size (bytes)** | Claude setting `builds.briefMaxBytes` | pipeline `settings.json` `briefMaxBytes` | `migrateSettings()` |

How an alias behaves: every reader still gets the field (`settings.maxAgents`, `settings.parallelPerAccount`,
`settings.autoQueue`, `settings.briefMaxBytes`), filled from the one key. A store that only has the old key (a fresh
checkout, a test) is read from it. Nothing writes an old key again: a save drops it (`maxAgents`), routes it to the one
key (`parallelPerAccount`, an account's `parallel`) or refuses it and says where the setting is (`autoQueue`,
`briefMaxBytes`).

Migration rule: when two copies disagree, the one saved last is kept and the decision is one line in
`settings-migrations.jsonl` next to the store (what was kept, what was dropped, both save times). One guard: a later
`maxAgents` above the limit never raises Builds at once, because only Brett raises that.

What the migration will do to the live values (read Nov 21, not run yet: it runs from main after the merge):

- Builds at once: 6 and 6 agree. `maxAgents` leaves `settings.json`. Nothing changes.
- Sessions per account: the default is 5 in both. The pipeline file was saved last (Nov 20, Job routing Nov 19), so the
  per-account numbers follow what the dispatcher was really using: **hulu0241 8 → 5 and mossesx-max- 8 → 5** in Job
  routing. That is the value in effect today (the dispatcher capped both at 5), now shown honestly. To really run 8 on
  one account, raise it once in Builds → Pipeline → Accounts (More sessions) or Job routing; Builds at once (6) still
  caps the total.
- `builds.maxParallel` = 1 (Nov 6) was already ignored. It stays in the Claude document, unread unless nothing else is set.
- `autoQueue` false and `briefMaxBytes` 122880 equal the Claude defaults: both leave the pipeline file. From then on
  the switch in Settings → Claude → Builds works again.

Defaults: with no file at all the cap is now the limit's default (8) instead of the queue's old 6. Brett's VPS has 6
saved, so nothing changes there.

**The "VPS limit 0 of 6" counter.** Cause: `build-limit.mjs` decided "I am the host" by whether `ps` works. The
console container has `ps`, so it counted its own processes (no builds), showed 0 and wrote that 0 over the host's
snapshot until the enforcer's next pass 30 s later. Fix: only the build host counts (`isBuildHost()`): the enforcer
records which machine it runs on (`build-limit-host.json`), and until that marker exists a container on the shared
store is never the host. Everything else reads the host's snapshot; a stale snapshot shows "?" (unknown), never zero.
Confirmed against the live console container before the fix (`live: 0, source: host` while 5 builds ran).
