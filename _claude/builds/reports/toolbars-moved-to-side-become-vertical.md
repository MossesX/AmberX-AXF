# Toolbars moved to the side become a vertical column (`toolbars-moved-to-side-become-vertical`)

Brett, Nov 16 2026: "If I move the toolbar to the left instead of the top, it needs to run down the side like a column instead of pushing all the content down."

Branch `claude/toolbars-moved-to-side-become-vertical`, Opus, steps s1–s3.

## What changed

**s1: side toolbars are a column (framework layout rule).**
- Layout `toolbarPosition` is now `top | bottom | left | right` (asset-types.json, layout.schema.json, control.json, `LAYOUT_ENUMS`, `types.ts`, `CHROME_MOVES.toolbar`).
- `compileLayout` (core/engines/layout.ts) gives a left/right toolbar its own `auto` grid column right beside `main` (inside nav and inspector). The grid rows match a layout with no toolbar, so nothing is pushed down. Top and bottom are still rows. On a phone the toolbar is a row on top.
- axf.css (tokens only): buttons stack top to bottom, the column is capped at `--fx-layout-nav-width`, scrolls down with snap when full, and shows icons only at `data-fx-medium`. At `data-fx-narrow` it goes back to a row. The Toolbar sets `aria-orientation="vertical"`.
- `runtime.layoutData()` returns the layout with its control@1 `tokens.layout` overrides. The shell and toolbar read it, so a Move shows at once.

**s2: Brett's Nov 16 extras.**
- (a) Tab groups: a tab group with a panel was already beside it (`.fx-tabframe`). A row-only tab group moved left/right now makes its host a two-column grid, so the row runs down the side of its siblings (axf.css). On a phone it is a row again.
- (b) Position (Top / Bottom / Left / Right) is in every toolbar's settings: the app toolbar sends it to the layout's `toolbarPosition`, the same as Move ▸. Workspace toolbars keep it per instance and dock by it (`wsToolbarPlace`). Tab groups already had Position and Move ▸.
- (c) "Change asset" is gone for toolbars: no context-menu item, no Asset tab in the settings dialog, and `chrome.pick` / `chrome.swap` refuse toolbars with a note (`CHROME_NO_SWAP`, `chromeCanSwap`). Other kinds keep their picker.
- (d) Hide switch on every toolbar and tab group (settings + context menu "Hide …"). App toolbar = the toolbar slot (hide engine). Tab groups and workspace toolbars = a per-instance `hidden` (a hidden tab row with a panel still shows the panel). Settings → Appearance → Visible parts lists hidden ones (`chromeHiddenList`), each with a switch to bring it back.

## API (all four the same: REST `/api/console-control`, MCP `console_action` / `console_control_*`, `axf console …`, AmberX voice)
- Move: `chrome.move:toolbar:app:left|right|top|bottom`, `chrome.move:tab-group:<id>:left|…`
- Position as a setting: `chrome.set:toolbar:<instance>:position:left`, or the control@1 token `tokens.layout` → `toolbarPosition` (REST / MCP control@1, `axf control`)
- Hide: `chrome.hide:<toolbar|tab-group>:<instance>:on|off|toggle`, or `chrome.set:…:hidden:on|off`; app toolbar also `slot.hide:toolbar:on|off`
- State: the layout tokens (`--fx-layout-toolbar-position`), `axf.chrome.<type>.<instance>` settings, `slot.hide` state; deep link `chrome.settings:<type>:<instance>` opens the dialog
- Change asset for toolbars: removed from every surface (actions refuse it)
