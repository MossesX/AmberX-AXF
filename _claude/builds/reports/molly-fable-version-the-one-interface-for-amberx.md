orchestrator's phase 2 downgrade, recorded on the build). Branch `claude/molly-fable-version-the-one-interface-for-amberx`.

## Result

Molly on main is the Opus shell (frames per app, xLayout's merged chrome, IDE panes, banners, nav sub menus). This
build adds the Fable layer the molly-opus build promised, on top of what is on main:

1. **molly-shell@1** (`framework/core/engines/molly-shell.ts`, Fable kernel engine): app instances, the host
   catalog a guest console announces for its host, host runs, the readable shell state. Two embed@1 messages carry
   it: `host-catalog` (host → guest console) and `host-run` (guest console → host). Fixture
   `framework/spec/fixtures/molly-shell.json` (generated by `spec/gen-molly-shell-fixture.mts`), check
   `spec/check-molly-shell.mts` (287 checks), in CI next to check-dock / check-xlayout / check-chrome.
2. **Docked multi-instance tabs.** An app may be open more than once: `console`, `console#2`… (eight per app, 24
   open). Each copy is its own kept-alive frame and its own view ("Console 2"); in IDE mode every copy is a dock tab
   (closing a tab closes the copy and back). Molly menu → Tabs (a nested menu: New tab → another copy of this app /
   AmberX / axHub / Console / Expenses; Next tab; Close this tab; What is open). Deep links may name a copy
   (`#/console#2/builds`). Kept per browser tab (session storage).
3. **Shared banner and widgets.** The banners plugin (console banner strip in Molly's banner region) stays; the
   apps' banner widgets (chrome@1 `widgets`, xlayout merge `widgets: merged`) are now drawn by Molly on the top
   toolbar edge, one per kind across the apps, a tap going back to the app that sent it. Before this build Molly
   dropped them (a known gap since xlayout s6).
4. **Nested menus.** The nav sub menus from molly-nav-submenus stay (each app's sections as nested groups); the
   Molly menu gained the nested Tabs → New tab menu; the per-app application menus stay one top-level menu per app.
5. **Molly-to-app messages.** xLayout's chrome host is per instance: a pick goes to the copy on screen (else the one
   Molly's view is on, else the first); each copy reports its own active page; `shown` / `show` are per copy.
6. **Full REST, MCP, CLI and voice control** through the console inside Molly (plugin `apps/molly/plugins/control`),
   see below.
7. Two bugs found on the way and fixed: xLayout's chrome fold re-entered itself through the runtime's nav-style
   subscriber (stack overflow: the merged nav never finished), and the app area no longer filled the main region
   because the framework now wraps every view in a skin scope (`fx-ui-scope`), so the frames measured 0 px high and
   stayed hidden. Both would have hit the next CI re-bake of Molly on main regardless of this build.

## Phase 2 (s2, Opus): tab row + and tab menu

s2's text repeats the request ("Build the molly apps fable"), and s1 already built that on Fable. So s2 (Opus,
downgrade recorded) took the next open piece from the multi-instance tabs work (molly-multi-instance-tabs s2):

- **+ on every dock tab row.** `DockHost` takes an optional `onNewTab(groupId)`; when it is set, every tab row in that
  dock shows a + button (`framework/react/windows/{DockHost,WindowHost}.tsx`, the existing `fx-iconbtn` chrome, no
  new CSS). Nothing changes for an app that does not pass it. Molly passes it: + opens another copy of the row's
  active app (`Console` → `Console 2`) in that row.
- **Tab menu.** Right-clicking a tab selects it and opens the row's menu (`tab-group` target, payload = the group).
  xLayout adds New tab of this app, Open this tab in a floating window, Open this tab in a new pane, and Close this
  tab, all through one action, `xlayout.tab:<new|float|pane|close>:<group>`. Closing the first copy also takes its
  tab out of the dock.
- API: the same commands as Molly actions (`molly.new-tab[:<app>]`, `molly.close-tab[:<instance>]`,
  `xlayout.open:floating|pane:<instance>`) on REST `POST /api/console/action`, MCP `console_action`, CLI
  `axf console action …` and voice, as in the table below. `xlayout.tab` is one more action on the same paths, but
  it needs a dock group id, so remote callers should use the instance-based actions.

## How every UI feature is reached without the UI (Brett, Nov 8 2026)

Molly hands each console frame inside it its catalog (screens: the apps, the open copies, the apps' pages;
settings tabs; dialogs; actions) as console-command@1 items under `host:` ids. The console announces them with its
own catalog, so the console server resolves them like any console item and the console carries the command back up
as `host-run`; Molly navigates / opens the settings tab or dialog / dispatches the action. No new server, no second
sign-in, and voice (AmberX → console commands) comes for free.

| Feature | Deep link / open | State | Actions | REST | MCP | CLI | Voice |
|---|---|---|---|---|---|---|---|
| Switch app | `#/<app>`; `console_open "<app>"` | `console_where` (`… · molly: Console`) | `molly.switch:<app>` | `POST /api/console/open {"screen":"axhub"}` | `console_open` | `axf console open axhub` | "Amber, open axHub in Molly" |
| New tab (copy) | `#/console#2` after it exists; `console_open "console 2"` | `console_list screens molly` lists copies | `molly.new-tab[:<app>]` | `POST /api/console/action {"action":"molly.new-tab:console"}` | `console_action` | `axf console action molly.new-tab console` | "Amber, run new tab console" |
| Close / next tab | — | same | `molly.close-tab[:<instance>]`, `molly.next-tab` | `/api/console/action` | `console_action` | `axf console action molly.close-tab console#2` | "Amber, run close tab" |
| IDE mode, pane layout, open in pane / floating | `console_dialog "pane layout"` | `molly.state` (toast) / `console_where` | `xlayout.ide`, `xlayout.layout`, `xlayout.open:pane:<instance>` | `/api/console/action`, `/api/console/dialog` | `console_action`, `console_dialog` | `axf console action xlayout.ide` | "Amber, run IDE mode" |
| Widgets strip | shown with the app's toolbar | in `console_list screens` as the app | a tap = the app's own item (`xlayout.run:<app>:<id>`) | `/api/console/action` | `console_action` | `axf console action xlayout.run console:w:builds` | — |
| Molly control settings | `console_settings "molly control"` | the panel shows counts, consoles joined, last command | settings `molly-control.on`, `molly-control.toast` | `POST /api/console/settings {"tab":"molly control"}` | `console_settings` | `axf console settings "molly control"` | "Amber, open Molly control settings" |
| Every other Molly settings tab / dialog | `console_settings` / `console_dialog` | `console_list settings molly` | — | same | same | same | same |

Readable state: `axf console where` answers with the console's screen and Molly's (`Builds · molly: Console 2`);
`axf console list screens molly` lists what Molly can show (19 screens in the browser run: apps, copies, the apps'
pages); the `molly.state` action (molly-shell@1 `shellState`: view, app, copies, which are on screen, IDE mode,
apps joined) says the same in Molly. A structured JSON read of the state through the API is not there yet: the
console's `where` carries only screen / label fields. Noted as a gap below.

## Deploy

Molly is a static image (`apps/molly/Dockerfile`) at molly.amberxai.com, redeployed from main after the merge
queue lands this PR (no Fable variant URL: the Opus shell is upgraded in place, nothing in it was removed). The
console must be redeployed too for the host catalog path (its console-commands client forwards host runs). Until
the console is redeployed, Molly's own items are not reachable remotely; the console inside Molly still is.
