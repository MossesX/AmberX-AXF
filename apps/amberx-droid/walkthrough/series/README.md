# AmberX in three minutes (demo video series)

Seven short browser walkthroughs, one topic each, recorded on live data. Build
`demo-video-series-three-minute-browser`. The scripts are in `scripts.mjs`. Each scene has `say` (the narration and
captions), `shot` (what the camera shows) and `staged` (marks a screen that isn't built yet; it is shown as a mock with a
visible Preview label). They reuse the 2-hour walkthrough pipeline in `../` (recorder, Piper TTS, assembler, player).

| # | id | Title | App | Skin | Staged scenes |
|---|---|---|---|---|---|
| 1 | voice-control | Talk to it: voice control in AmberX | amberx-droid (phone) | control-room | none |
| 2 | orchestrator-agents | How the orchestrator builds everything with agents | console-web | newsroom | none |
| 3 | plan-studio | Plan Studio: plan by talking, build with one tap | console-web | ledger | none |
| 4 | skins-tokens | Skins and hot-swappable tokens | console-web | atelier | none |
| 5 | ui-designer | The UI designer: screens from building blocks | console-web | clinic | the screen canvas (7) |
| 6 | axhub | axHub: your server, your approvals, your apps | axhub-web | windows | none |
| 7 | build-an-app | Building an app, start to finish | console-web + phone | atelier | library matrix, canvas, action API, install (4) |

The hero stories and deep dives (steps s5 onward, most with a 60-second cut) live in `more/`, one file per video; see
`more/README.md` for the extra fields (`kind`, `camera`, `short`, `facts`).

Check the scripts (shape, ids, skins, apps, running time 2:30 to 3:20 at 150 words a minute, and that any video with
staged scenes says "preview" out loud):

```bash
node apps/amberx-droid/walkthrough/series/check.mjs --table
```

## The staged designer mock (s2)

The full UI designer isn't shipped, so every staged scene that shows it (the UI designer video, the build-an-app video,
the library matrix and assembly view of the hero stories) is recorded on one mock page, `../designer-mock.html`,
generated by `mock/build.mjs`. A **Preview · not shipped yet** label never leaves the screen. The page is real where it can
be:

| What | Where it comes from |
|---|---|
| Every colour, size, gap, font, radius and border | the `--fx-*` token set of each of the six skins, compiled through the real engines (`mock/tokens.mts`: colour theme, style theme, surfaces, scrollbar, typography / density / sizing, layout, and the button, container, toolbar and tab-group styles the skin picks) into `mock/tokens.json` |
| The controls | `framework/ui/axf.css` inlined: toolbars (`role="toolbar"` + label), tabs, cards, tables, fields, chips, buttons, status bar |
| The parts palette | the asset type registry, `framework/schemas/asset-types.json`, grouped as it is there |
| The library matrix columns | `framework/catalog/libraries.json` (ids, modules, names) |
| The layout picker | `framework/assets/layout` |
| The time tracker's entries and week | sample rows, labelled **Sample data** on screen |

Scenes (`mock: '<id>'` on a staged scene; `check.mjs` refuses an unknown one): `canvas` (pick a layout, drop a toolbar,
grid, tabs, form), `grid` (sort; the toolbar's screen-reader label), `phone` (desktop + phone frame), `skin` (the picker,
each step switches skin and re-renders), `voice` (a spoken request arrives as a console-control call; a search bar lands),
`assets` (the approved screen saved as an asset), `app` (the time tracker's Today and Week screens assembled part by
part), `actions` (every action with its REST, MCP, CLI and voice entry), `matrix` (features × real libraries, ticks fill
in; `rows=` names the features).

```bash
node apps/amberx-droid/walkthrough/series/mock/build.mjs            # regenerate designer-mock.html
node apps/amberx-droid/walkthrough/series/mock/build.mjs --tokens   # recompile the skins' tokens first (npx tsx)
node apps/amberx-droid/walkthrough/series/mock/build.mjs --list     # scenes, steps, params, skins
node apps/amberx-droid/walkthrough/series/mock/shot.mjs matrix --skin ledger --step 3   # a screenshot (--all: every scene)
```

Driving it: in the recorder, `h.mock('matrix', { skin: 'atelier', rows: ['Receipts', 'Budgets'] })`, `h.step()`,
`h.skin('ledger')` (record.mjs serves the page at `https://walkthrough.local/mock`). In a browser,
`designer-mock.html#matrix?skin=atelier&rows=Receipts,Budgets`, and `window.wtMock` (`scene`, `step`, `skin`, `state`,
`scenes`, `skins`) does the same; `window.wtStep()` is the recorder's step hook. The mock is a recording prop, not a
console screen: it has no console-control address and ships with nothing.

## Recording (s3)

Every video is its own walkthrough for the recorder in `../` and is recorded on its own, in its own work folder
(`/opt/amberx-walkthrough-rec/series-<id>`):

| Walkthrough id | What |
|---|---|
| `series-<video id>` | the full video (35: the seven above and the 28 in `more/`) |
| `series-<video id>-60` | its 60-second cut (13) |

`walkthrough.mjs` turns a video into chapters → scenes with an `act` each, and splits a chapter where the device changes
(a phone scene inside a desktop video is recorded on the phone layout as its own piece; the assembler fits every piece
into the video's frame: 1920×1080 for desktop videos, 1080×1920 for phone ones). `acts.mjs` decides how each scene is
recorded:

| Kind | When | What the camera does |
|---|---|---|
| act | a hand-written act in `ACTS` | the exact clicks the shot needs (tabs, rows, the held call) |
| screen | a rule in `ROUTES` matches the shot | opens that screen of the live app (console, axHub web read live, writes kept in the browser; AmberX on demo data) |
| mock | a staged scene with `mock` | that scene of the designer mock in the video's skin, steps played |
| card | story b-roll, a staged scene with no mock, a terminal line, the Android hub app, the end card | a card on the video's skin that says what it is (B-roll, Preview · not shipped yet, Terminal, On the device) |

Desktop recordings show a visible arrow cursor that glides to every target and rings on a click (the real mouse follows,
so hover states show); phone recordings keep the touch dot. Every scene's visible text goes through the secrets scan.

```bash
node apps/amberx-droid/walkthrough/series/check.mjs --acts          # every cut: pieces, devices, act / screen / mock / card per scene
bash apps/amberx-droid/walkthrough/series/record.sh                 # the seven core videos, one after another
bash apps/amberx-droid/walkthrough/series/record.sh commute expenses-60
bash apps/amberx-droid/walkthrough/series/record.sh all             # every video and cut
ONLY=queue bash apps/amberx-droid/walkthrough/series/record.sh orchestrator-agents   # re-record one piece
```

Each run goes through the VPS heavy slot (`framework/cli/agent-slots.mjs`) and leaves `publish/` (MP4, captions,
chapters, poster) unpublished; s4 publishes.

## Narration, sync, player, socials, publishing (s4)

| Piece | How |
|---|---|
| Narration | Piper, one clip per scene (`../tts.mjs`), voice `en_US-kristin-medium` at speed 1. Adjustable per video like every walkthrough: AmberX → Walkthrough → pick the video → **Edit the voice** (voice, speed 0.75–1.3, any line), then Re-voice (only changed lines, no re-recording) or Re-record. The same edits: `POST /api/walkthrough/series-<id>/render` on the AmberX server, or `VOICE_OVERRIDES_B64=… WALKTHROUGH=series-<id> bash ../rebuild.sh` (walkthrough-voice@1). |
| Sync | the recorder holds every scene until its clip ends (plus a short beat), and the assembler cuts each scene to its clip, so the picture, the voice and the captions (one cue per sentence, `walkthrough.vtt`) line up by construction. |
| Player | AmberX's Walkthrough page lists every published video (a picker once there are more than four). Each player sits in its own skin scope, `ui:walkthrough-series-<id>`, so it can wear any skin: Settings → Appearance → Where, `node framework/cli/skins.mjs use amberx <skin> --scope ui:walkthrough-series-<id>`, the theme-manager routes or the `skin.scope` action. `chapters.json` carries the video's own `skin`; `SKIN=1 series/publish.sh` puts each player in it. |
| Socials | `social.mjs`: `walkthrough-social-9x16.mp4` (1080×1920), `-1x1` (1080×1080) and `-16x9` (1920×1080), H.264 + AAC with faststart, captions burned in, the picture fitted whole over a blurred fill. Made by the assembler for every series cut, offered as downloads on the player and served at `/api/walkthrough/series-<id>/walkthrough-social-<format>.mp4`. |
| Publishing | `publish.sh` runs the secrets scan again, then copies a recorded video into AmberX's data folder as walkthrough `series-<id>` (behind axHub's wall). |

```bash
bash apps/amberx-droid/walkthrough/series/publish.sh                 # every recorded video
bash apps/amberx-droid/walkthrough/series/publish.sh axhub commute-60
```

Reaching it without the UI: `GET /api/walkthrough/walkthroughs.json` (every video with its series, skin and cut),
`GET /api/walkthrough/series-<id>/chapters.json` (chapters, scenes, downloads), the files next to it; the
`walkthrough.play:series-<id>[:<chapter>]` action (deep link, Ctrl+K, voice "play the walkthrough"), `walkthrough.open:<chapter>`;
re-voice / re-record through `POST /api/walkthrough/series-<id>/render` (the console sends it to axHub as a veto call).
