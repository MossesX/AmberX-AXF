# Theme manager (console plugin)

`ai.amberx.axf.console.theme-manager` · built on Opus.

Roll colour / style / layout themes, or everything themeable, and choose exactly which tokens a roll may change.

- **Tree** of every token, built from `framework/schemas/asset-types.json` + the registered assets (new asset types appear by themselves): tri-state ticks, locks (never rolled), filter, presets (all / none / colors only / accents only / invert + your own named presets, saved server-side), "only" this branch. On a phone it drills down one level at a time.
- **Sane rolls** (`web/rollEngine.ts`): colour themes get a harmonious palette with contrast-checked text and status colours; numbers stay inside the range the known themes use; enums pick known values. Readability warnings for the active colour theme.
- **Live preview** through the engines (`registry.register` + `rt.swap` on `tm-preview-<type>-a|b`), undo/redo (50 steps), pin favourites, edit any value by hand, back to the saved look.
- **Save as asset**: one standard asset@1 per changed type (name, tags), kept in `.axf-console/plugins/theme-manager/themes/<type>/<id>.json`, registered on start; the ones you applied last come back on reload. Apply, rename, duplicate, export, import, delete. Built-in ids are refused, so built-ins are never changed.

- **Appearance and skins:** this plugin's page and Settings → Appearance are one shared panel (`AppearancePanel`, framework/libs/settings): Skin (picker with live preview, Apply, Reset) and the Use skin switch (off by default, this app only), Style / Colour / Layout theme, Visible parts, Navigation menu, Restore to default with one undo. With a skin on, a pick overrides that part only (a dot and Back to skin). Right-click any chrome for Restore to default too. Design packages show as skins. The format is skin@1 + app-look@1 (`framework/core/engines/skin.ts`, `framework/spec/APPEARANCE-SOURCE.md`). **Every asset type and every scope (build skins-asset-types, Nov 7 2026):** the panel also shows *Where the skin applies* (hub-wide → this app → a screen → a plugin, the nearer level wins; Follow the hub-wide skin switch; per-screen / per-plugin Inherit / Skin / Off) in three switchable layouts (rows, dialog, matrix) and *What a skin covers* (every registered asset type, grouped by how a skin reaches it: slot / parts / reference / bundle / none; skin-coverage@1, `framework/core/engines/skin-coverage.mjs`).

- **Skins as packages of sections (skin-sections@1, build skins-as-packages-of-slices, Fable, Nov 10 2026; Brett: "Every skin has to be a package of chunks. Every single thing has to be its own asset"):** a skin manifest only names one asset per section — colours (color-theme), design (style-theme), layout, behaviour (behavior-theme), typography, density, sizing, icons (icon-pack), controls (style-package), chrome (`chrome-set`, new: title bar, menus, toolbar, nav, context menus, widgets, spacing, hidden chrome) and parts (`style-parts`, new: per-type style tweaks). Every shipped skin and design package was converted (`framework/assets/chrome-set/*`, `style-parts/windows`, `style-package/windows` + `amberx`; design packages name their chrome set under `extras.chrome`); the asset-library seeds generate the chrome sets. Engine: `framework/core/engines/skin-sections.mjs` (section registry, the two bundle types, resolving, `mixSkins`, manifests, skin-package@1 export / import, slice catalog, SVG thumbnails), pinned by `spec/fixtures/skin.json` → `sections` and `spec/check-skin.mts` (which also fails on any monolithic skin or package left).
  - **Apply with picks** (Settings → Appearance → Choose…): the picker lists the skin's sections with checkboxes and previews; a left-out section keeps what is in force now (app-look@1 `skin.sections`: a section swapped for another asset, or null = left out). The console previews each change live.
  - **Mix = new skin:** a result drawn from more than one skin opens *Save as a new skin* (name, description, thumbnail captured from its colours and layout; Save as new / Apply without saving / Cancel). Saved skins go through the runtime's save sink to this plugin's `/themes` store and are registered in the app at once.
  - **Skin Builder** (nav → Plugins → Skin Builder, View → Look → Skin Builder…, action `theme-manager.skin-builder[:<skin>]`, screen `skin-builder`): slice library (search, by section, live hover preview) + pack template with one slot per section; drag a slice in (lib-dnd; on a phone Pick → tap), see empty and required slots, swap or clear, save a slot's current section as an asset of its own, After / Before, Save, Apply, Export (`<id>.skin.json`, skin-package@1 with the section assets inside), Import, Duplicate, Load to edit later. Snap animation on drop, slot highlights while dragging, desktop and phone layouts.
  - **API (all four the same):** routes `GET /skins/sections?category=&q=` (the slice library), `GET /skins/skin/{skin}` (one skin's sections), `POST /skins/sections` (`{section, id, name, from?: <skin> | data?}` — save a section as an asset), `POST /skins/build` (`{id, name, description?, from?, sections: {colors, design, …}}`), `GET /skins/export/{skin}`, `POST /skins/import` (`{package}`), `POST /skins/{app}/use` now takes `include` / `exclude` (section ids; the answer says `mixed` and `from`), `GET /skins/{app}/plan?skin=&include=` (the same without writing). They become MCP tools by themselves (plugin-commands@1: `theme-manager_skins_sections`, `theme-manager_skins_build`, …, and `plugin_run`), REST `/api/control/theme-manager/<command>`, and the CLI `node framework/cli/skins.mjs sections | skin | plan | use --include/--exclude | build | save-section | export | import` (saved assets in `AXF_SAVED_ASSETS_DIR`, this plugin's `themes/` folder when called from the console). Voice (AmberX through axHub) uses the same tools: "use the Windows skin but keep my colours", "build a skin from Aurora Night colours and the Windows chrome". In the app: actions `skin.use:<id>[:<sections>]`, `skin.section.back:<section>`, `theme-manager.skin-builder[:<skin>]`; deep links `console_open skin-builder`, `console_dialog axf.settings.skin <skin>`.

Routes (console token, 404 when disabled): `GET/POST /themes`, `PUT/DELETE /themes/{type}/{id}`, `GET/PUT /presets`, `GET /skins`, `POST /skins/{app}/use` (`{skin, scope?}`), `/off` (`{scope?}`), `/inherit` (`{scope}`), `/follow` (`{on}`), `/back` (`{slot}`), `/restore`, `/undo`, `GET /skins/{app}/at?scope=`, `GET/POST /skins/global` (`{skin}` | `off`), `GET /skins/coverage`, `GET /skins/covers/{skin}` (scope = `ui:<id>` | `plugin:<id>`). They become MCP tools by themselves (plugin-commands@1); the CLI is `node framework/cli/skins.mjs`. Voice: "use the Windows skin in the console" and "restore AmberX to default" go through these tools; inside an app, the actions `skin.use:<id>`, `skin.off`, `skin.restore`, `skin.undo`, `skin.inherit:on|off` and `skin.scope:<ui|plugin>:<id>:<on|off|inherit>[:<skin>]`.
Self-test: `python3 apps/console-web/plugins/theme-manager/test.py`.
